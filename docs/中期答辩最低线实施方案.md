# 基于最低可答辩线的中期答辩准备与实施方案

> **课题名称：** 基于 WebGPU 的工业多模态异常检测方法  
> **编制日期：** 2026-10-16  
> **适用阶段：** 尚未形成稳定 PyTorch 异常检测基线及 WebGPU 异常检测基线  
> **实施周期：** 3 天集中准备，后续 2～4 周完成正式 Go/No-Go 验证  
> **依据文件：**《研究内容v3.md》《中期准备.md》  
> **核心原则：** 中期答辩不要求提前完成全部 M1/M2，但必须以真实、可复现的技术证据说明研究已经启动，并具备继续实施的条件。

## 一、准备目标与结论

本次中期准备的目标不是在三天内完成论文全部研究，而是形成一个可信的阶段性闭环：

```text
研究问题明确
    ↓
技术路线与相关工作边界清楚
    ↓
真实数据进入真实模型
    ↓
得到可复现的异常分数、热力图或兼容性诊断
    ↓
说明哪些假设已验证、哪些仍待验证
    ↓
给出可执行的后续计划和失败退路
```

答辩时应呈现为：**A 阶段已经启动并获得基础证据，P1/P2 正在验证，M1/M2 属于后续拟研究内容。**

不得呈现为：已经证明 M1/M2 有效、已经取得零样本泛化提升、已经实现 WebGPU 加速，或已有完整跨数据集结果。

## 二、最低可答辩线

### 2.1 必须达到的四项要求

| 编号 | 必须达到的要求 | 最低验收证据 | 不合格表现 |
|---|---|---|---|
| G1 | 答辩材料完整 | 10～12 页 PPT、讲稿或进展报告、后续时间表 | 只有研究计划，没有当前进展页 |
| G2 | 数据与实验真实 | 数据来源、类别、非重叠划分、预处理和随机种子有记录 | 使用来源不明的图片或无法复现的样例 |
| G3 | 至少一条技术链路有真实输出 | PyTorch 异常分数和热力图，或明确、可复现的模型兼容性诊断 | 随机输出、静态假热力图、只展示网页界面 |
| G4 | 已完成、未完成和风险明确区分 | 一张状态表；所有图表标注“源域开发验证”或“未测” | 将 Oracle、计划或预测数值写成正式结果 |

其中 G1～G4 全部为硬要求。只有 PPT 而没有真实技术证据，不能视为达到最低线。

### 2.2 最低、稳妥和理想三个层级

| 层级 | 应达到的状态 | 答辩表述 |
|---|---|---|
| 最低线 | 数据流程可复现；PyTorch 有真实异常输出；PPT/报告完整；ONNX/WebGPU 有结果或明确失败记录 | 已建立初步实验链路，核心假设仍在验证 |
| 稳妥线 | PyTorch 基线可复现；至少 3 个源域类别有初步指标；ONNX CPU 与 PyTorch 基本一致 | A 阶段主体已跑通，正在验证浏览器端兼容性 |
| 理想线 | 在稳妥线基础上，WebGPU 完成真实 B=1 前向；有 Oracle ROI 初步结果 | P1/P2 基本通过，P3 获得初步证据 |

三天计划以“最低线必须完成、稳妥线尽量完成、理想线不强求”为准。

## 三、当前基础与差距审计

### 3.1 当前可利用的材料

截至本文编制时，工作区中已经存在：

- 《研究内容v3.md》：完整研究定位、M1/M2、实验协议及六个月路线；
- 《中期准备.md》：原三天冲刺安排；
- `clip-vitb32.onnx`：已有 CLIP ViT-B/32 ONNX 文件，可用于文件加载和浏览器环境排查；
- `clip_demo.html`、`clip-webgpu-demo.html`：早期浏览器 CLIP 探索页面；
- `工业缺陷图.png`：演示图片素材。

### 3.2 当前材料不能证明的事项

现有 ONNX 和网页不能直接作为本课题异常检测基线，原因包括：

1. 当前 ONNX 为 ViT-B/32，与研究方案优先采用的 ViT-B/16 不一致；
2. 现有页面主要输出图像级向量或文本图像相似度，不输出 Patch 异常图；
3. `clip_demo.html` 的文本向量为程序生成的模拟向量，不能作为真实多模态结果；
4. 现有预处理尚未证明与 CLIP 训练预处理一致；
5. 没有 PyTorch、ONNX CPU、WebGPU 三端一致性记录；
6. 没有训练日志、数据划分、评价指标和 ROI 实验。

答辩中可以将这些文件描述为“早期浏览器技术探索”，不能描述为“异常检测系统已经完成”。

### 3.3 当前环境风险

当前工作区可检查到的 Python 环境为 CPU 版 PyTorch，未发现 CUDA、ONNX Runtime、OpenCLIP 等完整依赖。正式执行前必须重新核实实际训练设备；如果另有 NVIDIA GPU 终端，应将训练转移到该设备，并保存真实环境信息。

| 时间 | 任务 | 具体输出 | 验收方式 |
|---|---|---|---|
| 09:00—09:30 | 建立 PPT 骨架和证据目录 | 11 页空白骨架、`midterm/` 目录 | 每页标题完整，防止实验占满全部时间 |

| 10:30—12:00 | 数据审计与最小划分 | 优先 1～2 类，记录图像与掩膜对应关系 | 输出 `source_split.csv` 和拼图 |
| 13:00—15:30 | 打通冻结 CLIP Patch 特征 | `[B,3,224,224] → [B,196,D]` 或等价输出 | 保存形状、数值范围和前向日志 |

#### Day 1 技术要求

- 输入固定为 `224×224`；
- 优先使用冻结 CLIP ViT-B/16；确实无法运行时记录原因，再采用 B/32 做兼容性排查；
- 记录 resize、crop/padding、RGB 顺序、CLIP mean/std；
- 明确提取层、是否去除 CLS Token、Patch 网格尺寸；
- 固定对象无关 Prompt，不使用目标域类别名；
- 训练/验证图像不重叠；
- 图像级分数暂按研究方案记录，但同时保留最大值和固定网格聚合用于诊断；
- 所有图注明样本类别和数据用途。

#### Day 1 止损规则

- **12:00 仍无法获得完整数据：** 缩减至一个类别，完成数据格式与掩膜检查；
- **15:30 仍无法提取 Patch 特征：** 停止训练，保存冻结 CLIP 前向和错误定位；
- **18:30 仍无有效热力图：** 不开始 ONNX 导出，优先修复数据、特征层或标签映射；
- **21:00 PPT 仍为空：** 停止技术开发，确保材料结构完整。

#### ONNX 一致性检查

固定 5～10 张输入，至少记录：

| 检查项 | 记录内容 |
|---|---|
| 输入 | shape、dtype、归一化、数值范围 |
| 输出 | `anomaly_map`、`image_score` 的名称和 shape |
| 数值差异 | 最大绝对误差、平均绝对误差 |
| 空间一致性 | 热力图差异图或相关系数 |
| 排序一致性 | 多样本异常分数排序是否一致 |
| 失败情况 | 不支持算子、动态 shape、内存或浏览器错误 |

推荐先以 FP32 验证正确性。若后续采用 FP16，应单独报告精度和性能变化，不能混合比较。

- 使用当前 ONNX Runtime WebGPU 推荐入口；

- 使用本地 HTTP 服务加载模型，避免 `file://`、CORS 和超大文件加载问题混淆；
- 首次推理和预热后推理分别计时；
- 页面只需图像输入、异常分数、热力图、设备和时间信息；

## 七、技术实施方案

### 7.1 数据协议

三天阶段只进行源域开发验证，不开展目标域正式测试。

建议：

- 优先选择图像和掩膜完整、缺陷明显且包含少量微小缺陷的 1～2 个类别；
- 稳妥线扩展到至少 3 个类别；
- 保存训练、验证文件路径清单；
- 所有划分固定随机种子；
- 训练和验证不重叠；
- 报告正常/异常样本数量和异常掩膜面积分布；
- 不根据 VisA 目标结果调整 MVTec 源域配置，反向实验同理。

答辩中必须说明本课题的“零样本”指：**目标域零训练、零调参、零阈值校准；源域允许使用异常图像和掩膜。** 该设定应称为跨数据集目标域零训练或辅助域监督的 ZSAD，避免被理解为完全无异常监督。

### 7.2 最小 PyTorch 基线

```text
输入图像 224×224
    ↓
冻结 CLIP ViT-B/16
    ↓
选定一个中间层 Patch 特征
    ↓
轻量 Adapter / 异常头
    ↓
固定正常/异常文本原型
    ↓
14×14 Patch 异常图
    ↓
图像级异常分数与可视化
```

最小配置：

| 项目 | 固定设置 |
|---|---|
| 主干 | CLIP ViT-B/16，冻结参数 |
| 输入 | RGB，224×224，CLIP 标准归一化 |
| 文本 | 对象无关正常/异常 Prompt 集成，离线计算 |
| 异常头 | 一个线性层或两层 MLP，不引入复杂模块 |
| 输出 | `anomaly_map [B,14,14]`、`image_score [B]` |
| 损失 | Focal Loss + Dice Loss |
| 优化目标 | 先验证真实异常信号，不追求三天内最优性能 |

为证明“多模态文本原型”不是形式性组件，后续正式实验应增加同参数量普通二分类头对照；该对照不属于三天硬要求，但必须进入后续计划。

### 7.3 最小评价指标

三天阶段至少保存：

- 验证 Loss；
- Image AUROC 或 Image AP；
- Pixel AP 或 Pixel AUROC；
- 正常、明显异常、微小异常的可视化；
- 至少一个误报或漏检案例。

样本过少时，指标必须标注“源域小样本探索性结果”，不能写成正式跨数据集结论。

### 7.4 ONNX 与浏览器接口

最小接口固定为：

```text
input:
  image         float32 [1,3,224,224]

output:
  anomaly_map   float32 [1,14,14]
  image_score   float32 [1]
```

中期阶段先导出静态 B=1。动态 Batch、`B=2/4`、Graph Capture 等放在基线稳定后验证。

浏览器只承担：

- 图像读取和预处理；
- ONNX Runtime WebGPU 前向；
- 热力图上采样和叠加；
- 显示模型、后端、分数和时间。

候选生成、动态 K、ROI 调度和融合不进入最低答辩线。

## 十四、中期后的 2～4 周实施安排

三天答辩准备不能替代正式研究验证。答辩后按以下顺序继续：

### 第 1 周：稳定基础模型

- 扩展至完整源域开发类别；
- 固定数据划分和评测脚本；
- 比较文本原型头与普通二分类头；
- 确认 Patch 特征层和基础指标；
- 完成可重复训练与日志归档。

### 第 2 周：稳定 ONNX/WebGPU

- 固定静态 B=1 正确性；
- 完成 PyTorch、ONNX CPU、WebGPU 一致性；
- 记录模型大小、加载、首次推理和稳定时延；
- 验证实际设备支持，不追求 Graph Capture。

### 第 3 周：验证局部观察价值

- 完成 224 全图、Oracle 1/2 ROI；
- 实现随机、网格、Top-K、Top-K+NMS；
- 统计 Region Recall@K 和 Tiny/Small 结果；
- 判断粗阶段是否能够找到缺陷。

### 第 4 周：Go/No-Go 决策

| 结果 | 决策 |
|---|---|
| P1～P4 基本支持 | 进入 M1，再进入固定 K 和 M2 |
| P1 不支持 | 修复或更换基础异常头，暂停 M2 |
| Oracle ROI 不支持 | 终止粗到细路线，启用缺陷保持备用方向 |
| Oracle 有效但 Top-K 无效 | 重点推进 M1 候选保持训练 |
| ROI 成本不可接受 | 限制 K/优化 Batch；无改善则退出动态 ROI 主张 |
| 相关工作高度重叠 | 与导师确认后收缩或修改创新点 |

第 4 周必须形成一页书面决策记录，不能无限延后核心可行性判断。

## 十六、最终执行原则

1. **先要真实输出，再要完整指标；先要完整材料，再要加分实验。**
2. 三天内最重要的技术成果是可复现的 PyTorch 异常图，不是复杂 UI。
3. ONNX CPU 一致性优先于 WebGPU 性能，WebGPU 正确性优先于动态 Batch 和优化。
4. Oracle ROI 只回答局部观察有没有上界价值，不能证明正式方法有效。
5. 所有实验必须区分源域开发、目标域正式测试和兼容性诊断。
6. 失败实验可以作为可信进展，模拟或夸大结果不能作为进展。
7. 中期答辩通过后，仍须在第 4 周前完成 P1～P4，才能判断是否正式进入 M1/M2。

本方案的最低交付不是“证明论文已经成功”，而是让评审看到：**研究问题成立、实施边界清楚、已经开展真实实验、当前结果可核查、后续决策有明确依据。**
